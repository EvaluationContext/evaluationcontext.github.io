LogicalIds and Variable Libraries Do the Same Job

A thought from FabFest on why logicalIds and Variable Libraries exist, how they can return noise in git

I spoke at FabFest today on Fabric-CICD: From Click Ops to DevOps. The talk felt like a bit of a chaotic stream of thought from where I was standing, but it seemed to land well. The useful part came afterwards, talking to people in the hallway, when a thought I had been dancing around for a while finally clicked. Obvious in hindsight, but worth sharing, so here is another stream of thoughts.

ObjectId¶

Every item in Fabric has an objectId, the GUID you see in the URL, unique to that item in that workspace. When items reference each other they do so by objectId, by name or URL, or by logicalId, depending on the team that built the item type.

That is fine in one workspace. Promote to another (dev test prod) and an objectId reference still points at the original item in the original workspace. Every environment has its own GUIDs, so every promotion means a round of GUIDs that have to change, and noise in git.

LogicalId¶

A logicalId is a GUID too, but it is only unique within a workspace. It lives in the item's .platform file and follows the item across environments, so the dev, test and prod copies all share one.

Microsoft Docs: Git source code format

The logicalId connects an item in a workspace with its corresponding item in a Git branch. Items with the same logicalIds are assumed to be the same. The logicalId preserves the link even if the name or directory change. Since a branch can be synced to multiple workspaces, it's possible to have items in different workspaces with the same logicalId, but a single workspace can't have two items with the same logicalId. -- Microsoft Docs: Git source code format

When a reference is stored as a logicalId, Fabric autobinds it: the objectId is swapped out on the way into git and swapped back on the way into the new workspace. Nothing in git changes between environments.

Variable Libraries¶

Variable Libraries replace the objectId with a reference to a variable. The item definition holds the variable name, and each workspace holds, outside of git, which value set is active determines what the variable resolves to.

The Same Job¶

This is the thought. They both do the same job, at least in respects to git. They keep references environment-agnostic, so the right item is referenced whichever workspace the definition lands in, and that removes GUID churn and noise from git. One is implicit and the platform resolves it, the other is explicit and you maintain the values.

The issue is that there are item types that support neither, so they have to be dealt with using fabric-cicd and parameter.yml. But you are overwriting objectId with the new environment's objectId on every deployment.

I feel this most in feature workspaces, which I provision for every feature branch by deploying with fabric-cicd, then connecting to git, and perform a commit, to lock in the GUIDs, so the branch and workspace are in sync, ready for a developer's to start working on it.

I also, begrudgingly, connect the dev workspace to git purely so the workspace relation nests feature workspaces under it. But with a rule, that this workspace should never be sync'ed. The risk being that is someone did, then they write objectId's from the last feature branch to merge into main, into the dev workspace.

Conclusion¶

LogicalIds and Variable Libraries are two implementations of one idea: get the GUIDs that change between environments out of the item definition, so one definition in git works in every workspace. It would, be nice if more items supported them.

My thoughts on Variable Libraries are softening, since I found that hidden deep in the fabric-cicd documentation is the fact that it sets the active value set during deployment if the environment and set names match. If autobinding was complete, you wouldn't even have to use item references](https://learn.microsoft.com/en-us/fabric/cicd/variable-library/item-reference-variable-type#how-it-works) to items within the same workspace. Item references would then only be required for cross-workspace references. But... I still have problems with item references. They need a objectId, so the item you are referencing already has to exist, which still makes them hard to use when trying to orchestrate deployments across multiple workspaces, which could be resolved if they supported logicalId instead.
